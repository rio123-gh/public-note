# JSON-LD（JavaScript Object Notation for Linked Data）

## 概要
- JSON-LDは、Linked dataをJSON形式で記述する規格、またはJSON形式で書かれたLinked dataを指します。
- Linked dataとは、あるデータをコンピュータにとって読みやすく、かつ他のWeb上のデータと容易に結び付けられるようにしようという考え方です。
- 仰々しい書き方がされていますが、JSONに対して型を導入して、プロパティ名や値のデータ型・フォーマットを限定しようというのが根底にあるアイデアだと理解しています。


- [JSON-LDの基礎](https://zenn.dev/esnir/articles/basic-jdon-ld)


## なぜJSON-LDが必要なのか？

- 例えば、人間がWebページを見て「東京タワー、3000円、10:00〜18:00」と書いてあれば、それが観光地の入場料や営業時間だとすぐに分かります。しかし、検索エンジンのロボットにとっては、ただの「文字と数字の並び」に過ぎません。

- JSON-LDを使ってデータを構造化（整理）して記述することで、ロボットに「これは『観光地』の名前で、これは『入場料』で、これは『営業時間』だよ」と正確に伝えることができます。


## 基本文法

### JSONの例
```json
{
  "name": "John Smith",
  "birthday": "2004/01/26"
}
```

### JSON-LDの例
```json
{
  "https://schema.org/name": "John Smith",
  "https://schema.org/birthDate": "2004-01-26"
}
```

### 何が違うのか
- 例えば人物を表すデータを書くことを考えます。一例として上のようなJSONが考えられますが、複数のウェブサイトがそれぞれ人物のデータを掲載するときには、それぞれ独特のプロパティ名が使われたり、国の慣習や個人の好みでデータのフォーマットが違ったりする場合がしばしばあります。
- ここでプロパティ名に指定されているURLはIRI (Internationalized Resource Identifier)と呼ばれる統一的な識別子で、これによってJSON-LDの各プロパティの性質を一意に特定しています。実際にこのURLにアクセスすると、値の型やフォーマットの明確に定義を確認できます。
- 例えば、JSON-LDで書き直すにあたり、誕生日のフォーマットを2004/01/26から2004-01-26へと変更しました。これは、今回プロパティのIRIに https://schema.org を使おうと決めたからです。（ここは決めの問題であり、JSON-LDを使うなら https://schema.org を使わなければならないということはありません）
- 具体的には、まずbirthdayプロパティに https://schema.org/birthDate を使うことに決めました。そこでbirthDateプロパティのドキュメントを読むと「値はDate型でなければならない」とあるため、日付は https://schema.org/Date で定められたフォーマットで指定する必要があることが分かりました。再び、今度はDate型のドキュメントを読むと「日付は ISO 8601 date format で書かれた値である」とあるため、誕生日はISO 8601の形式で書き直さなければならなかったのです。
- このようにして、プロパティ名とその値の文法的なフォーマット（シンタクス）・意味論（セマンティクス）とをウェブ横断的に統一します。
- なお https://schema.org は一般的な用途に使えるポピュラーなIRIを提供してくれるサイトです。専門的な分野でJSON-LDを使う場合は、そちらの規格で定められたプロパティと型を使うことが多いです。




## 高度な文法(3大コア機能。3大コアキーワード)
### 概要
- JSON-LDでは、先頭に@がついたプロパティは特別な意味を持ち、キーワードと総称されます。
- キーワードにはいろいろなものがある


### @context（文脈の定義機能）
- コアとしての役割： データの「意味の衝突」を防ぐ
  - インターネット上には無数の言葉があり、同じ単語でも文脈によって意味が変わります
  - （例：「タイトル」が本の題名なのか、肩書き・役職なのか）。
  - @context は、「このデータ内の単語は、このURLにある辞書を基準に解釈してください」と指定することで、世界中の機械が一切の誤解なくデータを読み解くためのベース（文脈）を作る機能です
- ブログでの解説
  - @contextは、これまでとは少し毛色の違うキーワードです。
  - JSON-LDでは、基本的にプロパティ名をIRIで書くことになるため、工夫しなければ素のJSONと比べて著しく可読性が落ちてしまいます。
  - そこで、@contextキーワードを使うと、IRIに対して人間が読みやすい名前を割り当てることができます。
  - @context: schema.orgという世界共通のデータ定義ルールに従いますよ、という宣言です。

- ❌ 無い場合（ただのメモ）
  - 機械の困惑： 「『アップル』…？ 果物のリンゴのこと？ それともiPhoneを作っている会社（Apple社）のこと？ どっちの辞書を読めばいいの？」
```JSON
{
  "name": "アップル"
}
```
- ⭕ 有る場合（世界共通データ）
  - 機械の納得： 「あ、schema.org のルールね！じゃあ、この後に出てくる項目はすべてWeb上の共通概念として解釈すればいいんだな」
```JSON
{
  "@context": "https://schema.org",
  "name": "アップル"
}
```

### @type（型・クラスの定義機能）
- コアとしての役割： データの「本質・ジャンル」を決定する
  - オブジェクト指向プログラミングでいう「クラス（型）」の指定にあたります。
  - そのデータが「モノ（本、映画、商品など）」なのか、「概念・出来事（イベントなど）」なのか、「組織や人間」なのかを宣言します。これがあることで、検索エンジンは「あ、これは映画（Movie）のデータだから、監督（director）や上映時間（duration）の情報を探せばいいんだな」と、次に続くデータをどう処理すべきかのロードマップを理解できます。
- ブログでの解説
  - @typeは何について書かれたページなのかを指定します。
  - 例えば、Book=本、Event=イベント、Organization=企業、LocalBusiness=地元の店舗など
  - プロパティ（name、author など）: @typeに合わせた詳細情報を入力します。

- ❌ 無い場合（ただのメモ）
  - 機械の困惑： 「佐藤健という名前は分かった。でも、これが『人間』の名前なのか、それとも彼が経営している『お店（店舗）』の名前なのか、あるいは『映画のタイトル』なのかが判別できない！」
```JSON
{
  "@context": "https://schema.org",
  "name": "佐藤 健"
}
```
- ⭕ 有る場合（世界共通データ）
  - 機械の納得： 「@type が Person（人間） だから、これは実在する人物のデータだね！じゃあ、この後に出てくる jobTitle は『職業』という意味だな」
```JSON
{
  "@context": "https://schema.org",
  "@type": "Person",
  "name": "佐藤 健"
}
```


### @id（ノードの識別機能）
- コアとしての役割： データの「本質・ジャンル」を決定する
  - オブジェクト指向プログラミングでいう「クラス（型）」の指定にあたります。
  - そのデータが「モノ（本、映画、商品など）」なのか、「概念・出来事（イベントなど）」なのか、「組織や人間」なのかを宣言します。これがあることで、検索エンジンは「あ、これは映画（Movie）のデータだから、監督（director）や上映時間（duration）の情報を探せばいいんだな」と、次に続くデータをどう処理すべきかのロードマップを理解できます。
- ブログでの解説
  - @idは、そのオブジェクトを一意に特定する識別子を指定します。識別子はIRIである必要があります。

- ❌ 無い場合（ただのメモ）
  - 機械の困惑： 「俳優の佐藤健さんと、近所の会社員の佐藤健さん、どっちのことだろう？ 他のWebサイトに書いてある『佐藤健』と同じ人なのかな？」
```JSON
{
  "@context": "https://schema.org",
  "@type": "Person",
  "name": "佐藤 健"
}
```
- ⭕ 有る場合（世界共通データ）
  - 機械の納得： 「この @id のURLが振られているということは、あの有名な俳優の佐藤健さんのことだ！ 他のサイトで同じ @id が使われていたら、全部この人のデータとして裏で繋ぎ合わせよう（Linked Data）」
```JSON
{
  "@context": "https://schema.org",
  "@type": "Person",
  "@id": "https://example.com/actors/takeshi-sato#char",
  "name": "佐藤 健"
}
```

### 複合的な例
- 例えば、「ある会社（A社）」が「ある人物（佐藤さん）」を雇っているという関係性を、この3つを使って表してみます。
  - @context があるおかげで、Organization や employee という単語の意味がGoogleに正確に伝わります。
  - @type があるおかげで、「株式会社A」が組織で、「佐藤 健」が人間だと分かります。
  - @id があるおかげで、この佐藤さんは「社員番号 sato-123」の佐藤さんであり、もし他のページ（例えば個人ブログやニュース記事）で同じ @id が登場したら、Googleは「あ、あの株式会社Aの佐藤さんね」と自動で情報をリンクさせることができます。
  - もしこれらが無いと、ただの「A、佐藤」という、プログラムを組んだ本人にしか意味の分からないテキストデータの集まりになってしまうのです。
```json
{
  "@context": "https://schema.org",
  "@type": "Organization",
  "name": "株式会社A",
  "employee": {
    "@type": "Person",
    "@id": "https://example.com/id/sato-123",
    "name": "佐藤 健"
  }
}
```

### 補足：その他のキーワード(なぜこの3つが「三大キーワード」と呼ばれるのか？)
- JSON-LDには他にも @graph や @language といったキーワードがありますが、「どこの辞書を使い（@context）」、「それが何であるかを定義し（@type）」、「世界中のデータと結びつける（@id）」 という3ステップこそが、Linked Data（データを繋ぐ技術）の根本であり、最も頻繁に使われるからです。



## webでの用途(リッチリザルト)
- Webサイトの情報を検索エンジン（特にGoogle）に正しく、効率よく理解してもらうためのデータ記述フォーマットで   す。
- 一言でいうと、**「人間のためのWebページを、ロボット（検索エンジン）にも100%理解できる形に翻訳して伝える仕組み」**です。


リッチリザルトの表示

Googleなどの検索エンジンがページの内容を完全に理解すると、検索結果の画面に通常のタイトルと説明文だけでなく、星評価、価格、イベント日程、FAQ（よくある質問）などが特別な形式で表示されるようになります。これを**リッチリザルト**と呼びます。

検索結果で目立つため、**クリック率（CTR）が向上する**という大きなSEO効果があります。


リッチリザルト（Rich Results）とは、Googleなどの検索結果画面において、通常の「ページのタイトル」と「説明文（スニペット）」だけの表示にとどまらず、画像、星評価（レビュー）、価格、FAQ（よくある質問）、レシピの調理時間といった追加情報が視覚的にわかりやすく表示される検索結果のことです。

昔は「リッチスニペット」や「リッチカード」などと呼ばれていましたが、現在は「リッチリザルト」という名称に統一されています。


どうすれば表示されるのか？
前回の回答で触れた「JSON-LD」などの構造化データを、WebサイトのHTMLコード内に正しく埋め込む必要があります。

Googleのクローラー（ロボット）がそのコードを読み込み、「このページには信頼できる商品レビューと価格の情報が含まれている」と判断すると、自動的に検索結果へ反映されるようになります。
