# Open Semantic Interchange (OSI)

- OSI は Cube や dbt のような「個別の独立した具現化ツール（実装製品）」ではなく、それらのツールの垣根を越えてセマンティック定義を相互運用するための**「共通規格（オープン標準仕様）」**という異なるレイヤーに位置する

なぜ OSI が今これほど重視されているのか、その位置付けと役割を整理します。

---

## 1. なぜ OSI が必要になったのか？（島構造の解消）

これまでセマンティックレイヤーは、各ベンダーが独自に進化させてきました。

* **dbt を採用した場合**: `dbt Semantic Layer` (MetricFlow の YAML)
* **Cube を採用した場合**: `Cube の YAML`
* **Looker を採用した場合**: `LookML`

結果として、**「dbt でせっかく定義した『売上（Revenue）』のロジックを、他の BI ツールや別の AI エージェントに持ち込めない（都度書き直す必要がある）」**という、セマンティックレイヤー自体のサイロ化（島構造）が新たな課題となっていました。

この「ベンダーロックイン」と「定義の再翻訳コスト」を解決するために、Snowflake、Salesforce、dbt Labs、Cube などの競合を含む業界リーダーたちが一堂に会し、共同で立ち上げた共通規格が **Open Semantic Interchange (OSI)** です。

---

## 2. ツール（Cube/dbt）とOSIの関係性

OSI は、ツールと競合するものではなく、ツールたちを結びつける**「共通言語」**です。

### レイヤー構造における OSI の位置付け

```text
【 物理レイヤー 】 Snowflake / Databricks / BigQuery 等
       ↓
【 定義・変換レイヤー 】 dbt / Cube / Looker / Salesforce（各製品の内部定義）
       ↓ 
★【 共通相互運用レイヤー：OSI (Open Semantic Interchange) 】★ ←★ここ！
       ↓ （共通のYAML形式でどこへでも持ち運べる）
【 消費レイヤー 】 各種BI、ThoughtSpot、AIエージェント（Text-to-SQL等）
```

### "Write Once, Query Anywhere" の実現

OSI が普及することで、以下のようなシナリオが実現します。

> [!IMPORTANT]
> **シナリオ例**
> dbt で定義したモデルを OSI 形式（Apache 2.0 ライセンスの標準 YAML）でエクスポートし、それを Cube や ThoughtSpot、あるいは Salesforce の AI エージェントにそのままインポートして、**1文字もロジックを書き直さずに同じメトリクスを利用する**。

これにより、定義のサイロ化を防ぎ、エコシステム全体でセマンティック情報をシームレスに持ち運ぶことが可能になります。

---

## 3. なぜ JSON-LD ではなく YAML が標準なのか？

OSI において YAML が標準（JSON もスキーマとして並行サポート）として採用され、セマンティックウェブで主流の **JSON-LD** がメインに使われないのには、両者の「出自」と「解決しようとしている課題」の違い、そして現代のデータエンジニアリングのトレンドが深く関係しています。

大きく分けて以下の 3 つの理由があります。

### ① 職能（ペルソナ）と開発フローの違い
最大の違いは、「誰が、どうやってその定義ファイルを書くか」という開発ワークフロー（**GitOps / Docs as Code**）への適応度です。

* **現代のデータ開発（Code-First）**:
  OSI に賛同している主要メンバー（dbt Labs、Databricks、Snowflake など）や、それを使うデータアナリスト・データエンジニアは、普段から dbt などのツールで YAML を使ってメタデータやモデルを管理しています。GitHub でプルリクエスト（PR）を出し、レビューを受け、マージするという運用が定着しているため、人間が視覚的に理解しやすく、差分（Diff）が綺麗に読める YAML が圧倒的に好まれます。
* **JSON-LD（Web/グラフ構造向け）**:
  JSON-LD は W3C が標準化した「Linked Data（ウェブ上のデータを意味的につなぐ）」のための規格です。`@context` や `@id`、`@type` といった特有のキー（RDF グラフの概念）が必要になり、人間が手書きでガバナンス（指標の管理）を行うには記述が冗長で直感性に欠けます。

### ② ターゲットとする「意味（セマンティクス）」のスコープ
「セマンティック」という言葉が指す意味の範囲が、両者で異なります。

| 特徴 | OSI (Open Semantic Interchange) | JSON-LD |
| :--- | :--- | :--- |
| **主な用途** | データの結合（Join）、計算式（Metrics）、集計軸（Dimensions）の定義 | Web 上のエンティティ（人、場所、商品など）の概念や関係性の定義 |
| **主な解決策** | どのツール（BI や AI）を使っても、「売上」の計算ロジックやテーブル結合を一貫させる | 異なるシステム間で、「このデータは同一の概念を指している」という一意の識別子（URI）を繋ぐ |
| **表現の形** | リレーショナルデータ、多次元キューブ、SQL への変換 | グラフ構造（RDF 構造） |

OSI は「BI ツールやデータプラットフォーム、AI 間で **SQL のロジックやメトリクス定義** を共通化する」ための規格です。そのため、グラフ構造をベースにした JSON-LD よりも、テーブル構造やリレーションシップ、数式（Expression）をシンプルに階層構造で表現できる YAML の方が仕様として素直にフィットします。

### ③ ツール・エコシステムの統合コスト
OSI は、すでに世の中にある多くの商用・OSS ツール（Tableau、Looker、dbt、Cube など）が持つセマンティックレイヤーを「相互に変換（ハブ＆スポーク）」できるようにすることを目指しています。

各ツールが社内で持っている既存のメタデータ構造を OSI にマッピングする際、プレーンな構造（YAML / JSON）であれば、パーサー（解析器）の用意やバリデーションスキーマ（JSON Schema）の適用が非常に容易です。
一方、JSON-LD をネイティブに扱うには、単なる JSON パーサーだけでなく、Linked Data や RDF、セマンティックウェブの知識、およびそれに対応した専用のグラフ処理ライブラリが必要になるため、ベンダー側の統合コスト（開発負荷）が跳ね上がってしまいます。

---

## 4. 将来的な共存とマッピング（Ontology Representation）

JSON-LD と OSI は完全に排他的な関係ではなく、レイヤーを分けて共存していくイメージです。

* **JSON-LD**: Web 全体でデータを繋ぐ「ナレッジグラフ」や「分散型 Web（ActivityPub など）」において強力な標準。
* **OSI**: 現代のデータウェアハウス（DWH）や AI エージェントが「迷わずに正しい SQL を発行するための共通の教科書（Metrics-as-Code）」。

なお、OSI のワーキンググループの中には **「Ontology Representation（オントロジー表現）」** というフォーカスグループも存在しており、将来的には OSI で定義したモデルを formal なオントロジー規格（RDF/JSON-LD などの方向性）へマッピングしていくブリッジ構造の議論も進められています。
