# オントロジー × セマンティックレイヤー 構築例

> **シナリオ**：あるECサイトで、ビジネス部門がSQLを書かずに売上分析できるようにする

---

## 全体像

| 概念 | 役割 | 例え |
| :--- | :--- | :--- |
| **オントロジー** | 現実のビジネス世界に「どんな概念があり、どう関係しているか」を定義したルールブック | 設計図 |
| **セマンティックレイヤー** | 複雑なDBとデータ利用者の間に入り、SQLの物理構造をビジネス用語に変換して提供するシステム層 | 翻訳機 |

---

## ステップ概要

1. **ビジネス概念の定義**（オントロジーの設計）
2. **物理データとのマッピング**
3. **セマンティックレイヤーの実装**
4. **データ消費**（BIツール・AIからの利用）

---

## ① ビジネス概念の定義（オントロジーの設計）

> このステップは、システムではなく **「人間同士の対話」** がメインになります。

物理的なDB構造は一旦忘れ、「私たちのビジネスの世界」をモデリングする。

- **エンティティの抽出**：顧客 / 注文 / 商品
- **関係性の定義**：「顧客」は「注文」を行う。「注文」は「商品」を含む。
- **ビジネスルールの定義**：
  - 「売上」＝「商品の単価 × 数量」
  - 「アクティブ顧客」＝「過去30日以内に注文した顧客」

**よく使われるツール**：Protégé、Miro / draw.io、Grafo

### ⚠️ よくある失敗：「サグラダ・ファミリア化」

- 全社のあらゆるデータを網羅した「完璧な設計図」を最初から作ろうとして、会議ばかりが続きシステム実装に進めないパターン
- IT部門だけで勝手に定義してしまい、現場の認識とズレるケースも頻発する

### ✅ 成功のポイント：小さく始めて育てる

- まずは「マーケティング部の、このキャンペーン分析に必要な概念だけ」など、スコープを極小に絞る
- ビジネス部門のキーパーソンを巻き込み、「うちの部署で『アクティブ顧客』と呼ぶ場合、具体的にどういう条件か？」をホワイトボードで一つずつ合意していくのがコツ

### 実装例：概念定義ドキュメント

```markdown
# ビジネス概念辞書：EC売上分析

## エンティティ（誰が・何を）
- **顧客 (Customer)**：サイトに会員登録しているユーザー。退会済みは含まない。
- **注文 (Order)**：決済が完了した取引。キャンセルされたものは「キャンセル注文」として区別する。

## 指標（Metrics）
- **総売上 (Total Revenue)**：注文ごとの (商品単価 × 数量) の合計。※消費税を含まない税抜価格で計算する。

## 切り口（Dimensions）
- **顧客セグメント (Customer Segment)**：
  - `新規`：初回購入から30日以内
  - `ロイヤル`：過去1年間で5回以上、かつ合計10万円以上の購入がある
```

## ② 物理データとのマッピング

> 美しい設計図と、泥臭い現実のデータベースを繋ぐステップ。

Step ① で作ったビジネス概念を、実際のDBテーブルと紐づける。

- 概念の「顧客」→ `users` テーブル
- 概念の「注文」→ `transactions` + `order_details` をJOINしたもの

**よく使われるツール**：dbt（data build tool）、Snowflake / BigQuery などのデータウェアハウス

### ⚠️ よくある失敗：セマンティックレイヤーへの「ゴミ処理」の押し付け

- 元のデータが汚い（顧客IDの形式がシステムごとに違う、表記ゆれがひどいなど）のに、無理やりセマンティックレイヤー上で結合・変換しようとするパターン
- 処理が重くなり、使い物にならないシステムになる

### ✅ 成功のポイント：データ基盤側での事前クレンジング

**"Garbage In, Garbage Out"** の原則通り、セマンティックレイヤーの手前（dbtによるデータマート作成など）で、データのクレンジングやIDの統一を済ませておくことが鉄則。

### 実装例：dbt モデルによるデータクレンジング（SQL）

```sql
-- stg_orders.sql（物理データと概念の橋渡し）
WITH raw_transactions AS (
    SELECT * FROM db.raw.transactions
),
raw_users AS (
    SELECT * FROM db.raw.users WHERE status != 'deleted'  -- 退会ユーザーを除外
)

SELECT
    t.order_id,
    t.customer_id,
    t.order_date,
    (t.price * t.quantity) / 1.10 AS net_revenue,  -- 税抜価格をここで計算
    t.status
FROM
    raw_transactions t
JOIN
    raw_users u ON t.customer_id = u.id
WHERE
    t.status != 'cancelled'  -- キャンセル注文を除外
```

## ③ セマンティックレイヤーの実装

> ここでルールを中央管理する。`description`（説明文）がAIエージェントにとっての「プロンプト」として機能する。

Step ② で作った綺麗なデータに対して、Step ① で定義したビジネスルールをYAML形式に翻訳する。

**よく使われるツール**：Cube、dbt Semantic Layer、LookML（Lookerの独自言語）

### ⚠️ よくある失敗：指標（Metrics）のスパゲッティ化

- 「総売上」「総売上_税抜」「総売上_返品除外」「総売上_USドル換算」など、似たような指標をYAMLに無限に定義してしまうパターン
- 結局「どれが正しい売上なの？」とユーザーが迷い、セマンティックレイヤーを入れた意味がなくなる

### ✅ 成功のポイント：指標はシンプルに、切り口で分ける

- 本質的な指標は「総売上」1つに絞る
- 「税抜/税込」や「地域」などは、指標そのものを分けるのではなく、**ディメンション（切り口）やフィルター**としてユーザー側で切り替えられるように設計する

### 実装例：dbt Semantic Layer の YAML 定義

```yaml
metrics:
  - name: total_revenue
    description: "総売上（税抜）。キャンセルされた注文は含まれません。会社の公式な売上報告に使用される最重要指標です。"
    type: simple
    type_params:
      measure: net_revenue

dimensions:
  - name: customer_segment
    description: "顧客のランク。'新規'（30日以内）や'ロイヤル'（年5回かつ10万円以上）などの文字列を返します。優良顧客の分析に使用します。"
    type: categorical
```

## ④ データ消費（BIツール・AIからの利用）

> 設定が完了すると、エンドユーザーは複雑なテーブル構造やJOINの書き方を知らなくてもデータにアクセスできるようになる。

**よく使われるツール**：Tableau、Metabase、ThoughtSpot、LLMを活用したデータエージェント

### ⚠️ よくある失敗：`description` の記述をサボる

- YAMLに `description` を書かずに実装してしまうパターン
- 人間がBIツール上で迷うだけでなく、LLMと連携させた際に**致命傷**になる
- AIは「計算式」だけでなく「説明文」を読んで文脈を理解し、正しいデータを引っ張ってくる

### ✅ 成功のポイント：人間にもAIにも伝わる辞書を作る

- 指標や切り口に対して、「これは何を意味するのか」「どういう時に使うべきか」を自然言語で丁寧に記述する
- ここをサボらないことで、AIに対して「先月のロイヤル顧客の動向を教えて」と雑に質問しても正確に解釈・回答してくれるようになる

## AIエージェントによる活用の仕組み

セマンティックレイヤーを挟むことで、LLMは **「複雑なSQLをゼロから記述する（ハルシネーションを起こしやすい作業）」** から解放され、**「定義済みのブロック（MetricsとDimensions）をパズルのように組み合わせるだけ」** になる。これがAIエージェントによるデータ分析の精度を飛躍的に高める最大の理由。

### 動作フロー：「先月のロイヤル顧客の総売上を教えて」

1. **意味の照合（Semantic Matching）**
   LLMはセマンティックレイヤーのYAMLを参照し、ユーザーの言葉をメタデータと照合する。

   | ユーザーの言葉 | YAMLのキー | Description |
   | :--- | :--- | :--- |
   | **総売上** | `total_revenue` | 「総売上（税抜）。キャンセルされた注文は含まれません。会社の公式な売上報告に使用される最重要指標です。」 |
   | **ロイヤル顧客** | `customer_segment` | 「顧客のランク。'新規'（30日以内）や'ロイヤル'（年5回かつ10万円以上）などの文字列を返します。優良顧客の分析に使用します。」 |
   | **先月** | `order_date` | 時間軸でフィルターをかける条件（`in_past: 1 month`） |

2. **安全なAPIリクエストの生成**
   LLMは実際のテーブル名や複雑なJOIN構文を直接知らなくてよい。セマンティックレイヤーに対して抽象的な命令（JSON）だけを投げる。

   ```json
   {
     "metrics": ["total_revenue"],
     "group_by": ["customer_segment"],
     "where": [
       {"dimension": "customer_segment", "operator": "equals", "value": "ロイヤル"},
       {"dimension": "order_date", "operator": "in_past", "value": "1 month"}
     ]
   }
   ```

3. **正確なSQLをシステム側が自動生成**
   セマンティックレイヤー側には物理DBのテーブル構造の正しい情報が定義されており、LLMからのリクエストを元に正確なSQLを自動生成する。

   ```sql
   SELECT
       SUM(t.price * t.quantity / 1.10) AS total_revenue
   FROM transactions t
   JOIN users u ON t.customer_id = u.id
   WHERE
       t.status != 'cancelled'
       AND t.customer_id IN (
           SELECT customer_id
           FROM transactions
           GROUP BY customer_id
           HAVING COUNT(*) >= 5 AND SUM(price * quantity / 1.10) >= 100000
       )
       AND t.order_date >= DATE('now', '-1 month');
   ```

4. **回答の生成**
   結果（例：`{"total_revenue": 5000000}`）を受け取ったLLMが、「先月のロイヤル顧客の総売上は **500万円（税抜）** でした。」とユーザーに回答する。

### なぜ精度が向上するのか

- **ハルシネーションの防止**：存在しないカラム名を指定するリスクを排除できる
- **ロジックの統一**：「税抜」「キャンセル除外」などのビジネスルールはYAMLに1箇所だけ書かれており、LLMは参照するだけなので計算式を間違えない
- **複雑なJOINの回避**：LLMは「ロイヤル顧客」という概念にフィルターをかける操作だけを考えればよく、より高度な分析にリソースを集中できる

> **補足**：YAMLに `description` がない場合、LLMは「定義が曖昧で文脈が理解できない」と判断し、分析リクエストを拒否するか、非常に不確かな回答を生成する。**「人間にもAIにも伝わる辞書を作る」** ことが、AIエージェント活用の成否を分ける鍵。
