# 次世代デジタルツインとIoTセマンティックモデルの体系的分析
## Brick Schema、AAS、RealEstateCoreを中心に

### デジタルツインにおけるセマンティックモデルの役割と全体俯瞰

サイバーフィジカルシステム（CPS）やデジタルツインの社会実装が急速に進展する中、物理空間に存在する機器、空間、センサー、およびそれらの相互関係を表現する「セマンティックモデル」が重要視されています。

*   **標準化の重要性**: 多様なベンダーの機器が混在する環境でシステム間の相互運用性を担保し、高度なデータ分析や機械学習、自律的制御を可能にするためには、統一された語彙とオントロジー（概念体系）が不可欠です。
*   **従来の課題**: 従来のビルディングオートメーション（BA）やファクトリーオートメーション（FA）では、運用データが十分に意味モデリングされておらず、手動のマッピングプロセスに多大な人的労力が費やされていました。
*   **現在の動向**: 特定のドメイン（製造、不動産、ビル、家電など）やアプローチ（メタデータタギングから厳密なRDFグラフモデルまで）に合わせて、複数の技術体系が並行して発展しています。
*   **本レポートの目的**: 主要技術の設計思想、データ構造、実装例、および規格間の相互運用性を体系的に整理し、網羅的に分析します。

### IoTセマンティックモデルおよびデジタルツイン関連技術の網羅的体系図

以下のツリー図は、対象とする主要ドメインと、それらが解決しようとしているレイヤーに基づいて各技術体系を分類したものである。

```text
├── 2. スマートビルディング・不動産ドメイン (Smart Buildings & Real Estate)

│   │   ├── RealEstateCore (REC) : 不動産運用・ビジネスロジックの統合
│   │   └── BOT (Building Topology Ontology) : ビルの純粋な空間トポロジー
│   │

│   └── C. 建築構造・物理モデリングレイヤー (BIM)

└── 3. クロスドメイン・スマートアプライアンス領域 (Smart Appliances / General IoT)
    └── SAREF (Smart Applications REFerence Ontology)
        ├── SAREF4BLDG (ビルディングドメイン拡張)

        ├── SAREF4CITY (スマートシティ拡張)
        └── SAREF4AGRI (農業ドメイン拡張)
```

この体系図から読み取れる重要なインサイトは、各標準規格が排他的なものではなく、デジタルツインの構築において相互に補完し合う関係にあるという点である。以下の表に、主要なセマンティックモデルの対象領域と技術的特徴の比較を示す。

| 規格名称 | 主な対象ドメイン | アプローチ / 基盤技術 | 特徴と位置づけ |
| :--- | :--- | :--- | :--- |
| **AAS** | インダストリー4.0・製造業 | メタモデル (JSON, XML, AASX, RDF) | 物理的アセットのデジタル表現。サプライチェーンを跨ぐデータ交換の標準インターフェース。 |
| **RealEstateCore** | 不動産ポートフォリオ管理 | オントロジー / グラフ (RDF, DTDL) | 建物運用、ビジネス管理、IoTを統合。Azure Digital Twinsとの親和性が高い。 |
| **Brick Schema** | ビルディング設備・制御 | オントロジー / グラフ (RDF, OWL) | 空調・照明等の設備トポロジーとセンサーの関係を厳密なグラフで表現し、高度な分析を可能にする。 |
| **Project Haystack** | ビルディング設備・制御 | タギング (メタデータ) | アセットに対して構造化されていないタグを付与する手法。導入が容易で普及率が高い。 |
| **BOT** | 空間トポロジー | オントロジー (OWL) | ビル、階、部屋といった空間の包含関係のみを記述する軽量オントロジー。他規格との統合の基盤となる。 |
| **SAREF** | クロスドメインIoT | オントロジー (OWL-DL) | デバイス、機能、タスクを中心にモデリング。ETSI標準であり、oneM2M等の通信規格と深く連携する。 |
| **IFC** | 建築情報モデリング (BIM) | STEP, XMLベース | 建物の物理的・幾何学的な3D構造情報を提供するが、機器の動的な機能やポイントの記述には不足がある。 |

次章以降では、このツリー図に位置付けられた各主要技術体系について、そのアーキテクチャ、具体的なデータ表現例、および他規格との差異や統合の動向について詳細な洞察を提供する。

## 1. 産業用デジタルツインの基盤：Asset Administration Shell (AAS)

### 1.1 AASの設計思想とアーキテクチャ

Asset Administration Shell（AAS：資産管理シェル）は、Industry 4.0の枠組みにおいて物理アセットとデジタル世界を統合する標準インターフェースです。

*   **役割と位置づけ**: 「Reference Architecture Model Industrie 4.0 (RAMI 4.0)」の中核として、企業間や製品ライフサイクル全体（設計、製造、運用、保守）におけるセキュアかつ相互運用可能なデータ交換を保証します。
*   **モジュール構造**: 
    *   **外殻（シェル）**: 物理アセットを一意に識別し、管理する役割を持ちます。
    *   **サブモデル（Submodel）**: 独立した情報カプセルであり、エンジニアリングデータ、時系列データ、CO2排出量など、用途に応じたデータを柔軟に追加・参照可能です。
*   **実装環境**: AASX server, Eclipse BaSyx, FA3ST service, NOVAAS などのツールがあり、石油化学プラントなどのデジタルツイン適用においては、特に Eclipse BaSyx が高いパフォーマンスと拡張性を示しています。

### 1.2 コアコンポーネントとセマンティクスの確保

AASのメタモデルは以下の主要要素で構成され、高度なセマンティック（意味論）の統一を実現しています。

*   **Identifiers（識別子）**: 
    *   グローバルな識別子（IRIやIRDI）を用い、アセット（`GlobalAssetId`）、AAS、サブモデルを一意に識別。
    *   自己管理型アセットは独自の `GlobalAssetId` を持ちますが、共同管理型アセットはBOM（部品表）サブモデル内で関係性として定義されます。
*   **Submodels（サブモデル）**: 
    *   特定のドメイン情報を構造化した構成要素。
    *   標準テンプレートとして「Digital Nameplate（デジタル銘板）」、「Technical Data（技術データ）」、「Time Series（時系列データ）」などが定義されています。
*   **SubmodelElements（サブモデル要素）**: 
    *   サブモデル内部のプロパティ群であり、メタモデル上で `Qualifiable`（修飾可能）かつ `HasSemantics`（意味論を持つ）要素として扱われます。
*   **MetadataとDictionaries**: 
    *   各要素の意味を機械可読にするため、ECLASSやIEC CDDといったグローバルな辞書への参照リンク（`semanticId`）を保持します。

### 1.3 AAS REST API V3とクエリ言語の実装

最新のAAS仕様（V3）では、大規模データの効率処理のために REST API 仕様が明確に定義されています。

*   **シリアライゼーション修飾子 (Serialization Modifiers)**: URL構造に加え、高度なデータ制御が可能です。
    *   `?level=deep`: 階層の深部までデータを一括取得。
    *   `?extent=withoutBlobValue`: バイナリデータを省略し、帯域を節約。
*   **専用クエリ言語**: 
    *   リポジトリから特定条件のインスタンスを検索するための仕組み。
    *   JSON Schemaに基づく比較演算子（`$eq`, `$le`, `$ne`等）とフィールド識別子（`$aas#idShort`等）を使用し、「製造年月日が一定以前のモーター」などの複雑なクエリをAPIレイヤーで直接実行できます。
    *   レジストリやAPIレベルで、カーソルベースのページネーションが標準実装されています。

### 1.4 具体例：Digital Nameplate（デジタル銘板）のJSONモデリング

AASのユースケースとして最も普及が進んでいるのが「Digital Nameplate（デジタル銘板）」です。物理機器に印字されたメーカー名や定格電力、製造番号などの属性情報を標準化されたプロパティ構造で提供し、システム統合を自動化します。

以下は、あるモーター機器のデジタル銘板サブモデルを表現したJSON構造の具体例である。

```json
{
  "assetAdministrationShells": [
    {
      "id": "https://example.com/ids/aas/pump_123",
      "idShort": "PumpAAS",
      "assetInformation": {
        "assetKind": "Instance",
        "globalAssetId": "https://example.com/ids/asset/pump_123_raw"
      },
      "submodels": [
        {
          "type": "ModelReference",
          "keys": [
            {
              "type": "Submodel",
              "value": "https://example.com/ids/sm/digital_nameplate_123"
            }
          ]
        }
      ]
    }
  ],
  "submodels": [
    {
      "id": "https://example.com/ids/sm/digital_nameplate_123",
      "idShort": "DigitalNameplate",
      "submodelElements": [
        {
          "idShort": "ManufacturerName",
          "semanticId": {
            "type": "ExternalReference",
            "keys": [
              {
                "type": "ConceptDescription",
                "value": "0173-1#02-AAO677#002"
              }
            ]
          },

          ],

```

このモデルが示す重要なインサイトは以下の通りです。

*   **セマンティクスの固定化**: `ManufacturerName` などのプロパティは自然言語に依存せず、グローバル辞書（ECLASS等）のIRDI/IRIを参照する `semanticId` によって一意の意味が伝達されます。
*   **多言語のサポート**: `MultiLanguageProperty` を使用して言語ごとの表記を構造レベルで内包できます。
*   **更新の容易性**: `PATCH /submodel/$value` リクエストによる部分更新などをサポートし、安全に上書きできます。

## 2. スマートビルディング設備のセマンティック記述：Brick Schema

### 2.1 Brick Schemaの設計思想とオントロジー的優位性

Brick Schemaは、商用ビルディングにおける物理的、論理的、および仮想的なアセットを対象としたオープンソースの標準化オントロジーです。

*   **目的**: 空調（HVAC）、照明、防災、セキュリティなどの多様で非標準的なビル資産と、それらの関係性を一貫したセマンティック技術（RDF/OWL）を用いて統合表現します。
*   **オントロジー的優位性**:
    *   従来のBMS（ビル管理システム）や Project Haystack で用いられてきた「タギング」は、一貫した構文規則がなくアドホックなタグ付が発生しやすい課題がありました。
    *   対照的に、Brick Schema は厳格なグラフベースのオントロジーを採用し、アセット分類や包含関係を明確に定義するため、グラフベースの機械学習やNLP（自然言語処理）アルゴリズムとの互換性が向上します。

### 2.2 コアデータモデルと階層構造

Brick Schemaのオントロジーは、主に以下の3つのクラス階層を根幹として構成されています。

*   **Location（空間）**: 建物の物理的・論理的空間（ビル、階、部屋、ゾーンなど）。
*   **Equipment（設備）**: 物理的な機器（空調機[AHU]、VAVボックス、ボイラー、チラー、煙感知器など）。
*   **Point（ポイント）**: システム間のデータの入出力を担う概念（センサー[測定値]、コマンド[制御命令]、セットポイント[目標値]、ステータス[状態]、パラメータなど）。

これら3要素を結合するために、以下のような標準的な関係性（Relationships）が用いられます。
*   `feeds`: 設備が空間や他の設備に物理的に空気を供給する関係。
*   `hasPart`: 設備が別の設備の一部を構成する関係。
*   `locatedIn`: 設備がどの空間に配置されているかを示す関係。
*   `isPointOf`: データポイントがどの設備に紐付いているかを示す関係。

### 2.3 実装エコシステムとPython API

Brick Schemaは、SQLiteなどのデータベースをバックエンドとし、Pythonの `brickschema` パッケージを通じて操作できます。

以下のスクリプトは、オントロジーファイル（`test.ttl`）を読み込み、推論実行と SQL ORM を介した自動集計を行う例です。

```python
from brickschema.graph import Graph
from brickschema.orm import SQLORM, Equipment

# デフォルトのBrickオントロジーとユーザー定義モデルのロード
g = Graph(load_brick=True)
g.load_file("test.ttl")

# 推論エンジンの実行とSQLiteデータベースへのORマッピング
g.expand("owlrl")
orm = SQLORM(g, connection_string="sqlite:///brick_test.db")

# 各設備に関連付けられたポイント（センサーやコマンド）を反復処理
for equip in orm.session.query(Equipment):
    print(f"Equipment {equip.name} is a {equip.type} with {len(equip.points)} points")
```

このコード例が示す重要なインサイトは以下の通りです。

*   **推論エンジン（Reasoner）の活用**: `g.expand("owlrl")` によって、明示的に記述されていない関係性をクラス階層の論理定義から自動的に補完・推論し、クエリを容易にします。
*   **他規格とのアライメント**: `g.load_alignment('BOT')` のように、他のオントロジーとのマッピングファイルをロードして、データ記述を相互運用する仕組みが提供されています。

### 2.4 具体例：空調設備と部屋のグラフモデリング (Turtle形式)

実データとしては、カリフォルニア大学バークレー校が公開する「Mortardata」などがあり、エネルギー最適化や居住者中心の制御（OCC）の検証に利用されています。

以下は、空調設備（AHU、VAV）から部屋（Room）への気流供給、および温度センサーの配置を示すTurtle (.ttl) フォーマットの実例です。

```turtle
@prefix brick: <https://brickschema.org/schema/Brick#>.
@prefix bf: <https://brickschema.org/schema/BrickFrame#>.
@prefix rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#>.
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#>.
@prefix mybuilding: <http://example.com/mybuilding#>.

# 空間とゾーンの定義
mybuilding:floor_1 a brick:Floor.
mybuilding:hvaczone_1 a brick:HVAC_Zone.
mybuilding:room_1 a brick:Room ;
    bf:isPartOf mybuilding:floor_1, mybuilding:hvaczone_1.

# 設備の定義とトポロジー（feeds: 物理的な供給関係）
mybuilding:ahu_1 a brick:AHU ;
    bf:feeds mybuilding:vav_1.
mybuilding:vav_1 a brick:VAV ;
    bf:feeds mybuilding:hvaczone_1.

# データポイント（センサー）の定義と設備への帰属
mybuilding:ztemp_1 a brick:Zone_Temperature_Sensor ;
    bf:isPointOf mybuilding:vav_1.
```

このモデルを解釈することで得られるメリットは以下の通りです。

*   **因果関係の自律追跡**: 「特定の部屋の温度異常が検知された際、影響するVAVや、大元の冷熱源AHUはどれか」という経路をグラフ探索によって自動で特定可能。
*   **トポロジーの明文化**: 配管の正確な3D座標等を持たずとも、設備の論理的な接続トポロジーを完全記述できるため、故障検知（FDD）等で非常に強力に機能します。

## 3. 不動産管理と空間モデリングの統合：RealEstateCore (REC)

### 3.1 RealEstateCoreの全体像と提供価値

RealEstateCore（REC）は、不動産ポートフォリオデータからデジタルツインを構築するためのモジュール式オントロジーです。

*   **ビジネス面への注力**: Brick SchemaやAASが制御等のテクニカルな側面に重きを置くのに対し、RECはテナント管理、施設メンテナンス、財務的側面など「プロパティマネジメント（ビジネスと不動産運用）」にフォーカスしています。
*   **4つのドメインの架け橋**: 新規に規格を置き換えるのではなく、「ビジネス管理」「BIM（建築）」「BMS（設備制御）」「IoTテクノロジー」を実用的に接続（ブリッジ）することを目指しています。

### 3.2 モジュール構造の進化と他規格との統合

バージョン3.3におけるモジュール再編により、外部の業界標準との親和性が大幅に向上しました。

| モジュール名 / 統合された外部標準規格 | 機能と役割 |
| :--- | :--- |
| **Spaces / BuildingElements**<br>(W3C BOT に準拠) | 建物の物理的な空間（部屋、階など）と構造要素（壁、屋根など）を明確に分離。トポロジー構築の基礎となる。 |
| **Asset / Capability**<br>(Brick Schema との共同開発に基づく拡張) | ビル内に設置される設備（HVACなど）と、それらが持つセンシング・アクチュエート能力（Capability / Points）を記述する。 |
| **LogicalDevice**<br>(独自拡張およびIoTエッジモデル) | クラウドにデータをプッシュするソフトウェアインスタンス（IoT Edgeモジュール等）やBMSシステム自体をモデリングする。 |
| **Units**<br>(QUDTオントロジーの部分的統合) | 物理量と単位系を定義。REC内のデータプロパティの範囲としてQUDTの単位を割り当て、セマンティクスを微細化する。 |

このモジュール構造により、以下のようなインサイトが得られます。

*   **トポロジー関係の厳格化**: `isPartOf` や `hasPart` は「同一タイプのエンティティ間（空間同士、設備同士など）」に限定。
*   **ナビゲーションの予測可能性**: タイプが異なるエンティティ間の関係記述（例: 設備がどの部屋にあるか）には、専用のプロパティ（`locatedIn`, `includes`, `isCapabilityOf` など）を別途定義することで、グラフ探索のバグを防ぎます。

### 3.3 Azure Digital TwinsとDTDLによる実装例

RECは Microsoft の Azure Digital Twins で採用されている「DTDL (Digital Twins Definition Language)」モデルと深く統合されています。

以下は、DTDL形式で記述されたRECベースのRoomインターフェースの完全なJSON定義例である。

```json
{
  "@id": "dtmi:com:example:Room;1",
  "@type": "Interface",
  "@context": "dtmi:dtdl:context;2",
  "displayName": "Room",
  "extends": "dtmi:com:example:Space;1",
  "contents": [
    {
      "@type": "Property",
      "name": "temperature",
      "schema": "double",
      "unit": "degreeCelsius"
    },
    {
      "@type": "Relationship",
      "name": "hasSensor",
      "displayName": "Has Sensor",
      "target": "dtmi:com:example:Sensor;1"
    },
    {
      "@type": "Relationship",
      "name": "servedBy",
      "displayName": "Served By HVAC Zone",
      "target": "dtmi:com:example:HVACZone;1"
    }
  ]
}
```

このモデルが示すアーキテクチャの強みは以下の通りです。

*   **有向グラフ表現の実現**: JSON-LDを利用し、各キーが関係のエッジとして機能。異なるシステムや組織間で標準化された意味論（`@context`）を提供します。
*   **モデル継承（extends）のサポート**: Roomを継承した様々な空間（Hallwayなど）を透過的に定義できるため、現実世界の複雑な建築・運用要件に対応できます。

## 4. セマンティック・ランドスケープを補完する関連技術

### 4.1 Project Haystack

Project Haystackは、スマートビル分析のために開発されたオープンソースのデータタグ付けイニシアチブです。

*   **技術基盤**: グラフや関係性ではなく「メタデータタギング」を基盤とします。例えば、給気温度センサーは `Sensor`, `Air`, `Temperature`, `Discharge` といったテキストタグを組み合わせて表現します。
*   **メリット**: コンセプトが非常に直感的であり、学習コストが低いため、対応APIやサードパーティのエコシステムがすでに成熟しています。
*   **デメリット**: 厳密な構文規則や因果関係を表現できないため、システムごとにアドホックな設計になりやすい課題があります。現在は、次世代標準である ASHRAE 223P へ向けて Brick Schema との調和・共同開発が進められています。

### 4.2 BOT (Building Topology Ontology)

W3Cの Linked Building Data コミュニティによって策定された空間構造特化の軽量オントロジーです。

*   **特徴**: `bot:Site`、`bot:Building`、`bot:Storey`、`bot:Space` といった基礎的なクラスと、包含・隣接関係のみに絞った「ミニマリズム」を特徴とします。
*   **役割**: 複雑な設備能力などを排除した共通のベースライン（背骨）として、Brick Schema や REC など他のオントロジー同士を空間情報でマッピングするためのハブとして機能します。

### 4.3 SAREF (Smart Applications REFerence Ontology)

ETSI（欧州電気通信標準化機構）によって策定された、IoTデバイス向けの共通モデルです。

*   **適用ドメイン**: ビル（SAREF4BLDG）に限らず、製造（SAREF4INDU）、スマートシティ（SAREF4CITY）、農業（SAREF4AGRI）など広範な垂直統合ドメインを持ちます。
*   **設計概念**: 「機能（Function）」を実行することで「タスク（Task）」を達成する「デバイス（Device）」という概念構造。

| クラス | 概念の定義と具体例 |
| :--- | :--- |
| **`saref:Device`** | 特定のタスクを達成するために設計された有形のオブジェクト。用途に応じてアプリケーション固有に拡張される（例：`saref:Sensor`, `saref:Actuator`, `saref:Appliance`）。 |
| **`saref:Task`** | デバイスが達成しようとする究極の目的（例：安全性確保、空調快適性維持、エネルギー効率最適化）。 |
| **`saref:Function`** | タスクを達成するためにデバイスが実行する機能（例：センシング機能、メータリング機能）。 |
| **`saref:State`** | 実行中の機能に応じてデバイスが取り得る状態（例：On/Off、Open/Close、マルチレベル状態）。 |
| **`saref:Commodity`** | デバイスが消費・生産する対象（例：電力、水、ガス）。 |

## 結論と規格間の統合的展望

本レポートから導き出される重要な結論は、デジタルツイン技術が「単一の標準ですべてをカバーする」段階から、**「各ドメインに特化したモジュラー・オントロジーの相互運用と協調」**へとシフトしているという事実です。

*   **製造エコシステムのプラグ・アンド・プレイ化**: AAS（Asset Administration Shell）の V3 API クエリや semanticId を用いることで、サプライチェーン間でのシームレスなアセットライフサイクル管理を実現。
*   **インテリジェントビル制御の自動化**: Brick Schema のグラフベースの論理構造により、設備とセンサーのトポロジー関係から、高度な障害検知（FDD）やエネルギー最適化を可能に。
*   **ビジネスとテクノロジーの統合ハブ**: RealEstateCore（REC）が Brick や W3C BOT とアライメントすることで、ビジネスとしての「テナント契約」と、IoTの「空調機器データ」を Azure Digital Twins 上で統合的に分析可能に。

### 設計者・インテグレーターへの実践的提言
*   **最適な標準のハイブリッド選定**: 要件がどのレイヤー（空間、設備制御、資産管理、製造）に属するかを整理し、適したセマンティック標準を選択的に組み合わせること。
*   **標準化動向の追跡**: ASHRAE 223P などの規格調和プロセスやオントロジー間の動的マッピングを追跡することで、ベンダーロックインを防ぎ、将来的に拡張性のあるデジタルツイン環境を構築することが必須です。
