# ナレッジグラフとセマンティック技術の全体像（完全版）

データを単なる「表」ではなく「意味を持ったネットワーク」として扱い、AIやシステムに高度な推論をさせるための技術体系を、データアーキテクチャのベストプラクティスである**「4層のレイヤーモデル」**に基づき整理します。各層において「概念（考え方）」と「実装（規格・ツール）」を明確に切り分けています。

---

## 1. テクノロジースタック（4層レイヤーモデルと用語集）

### Layer 1: スキーマ・モデリング層（設計図とルールの定義）
世界をどのようにデータ化するか、その「型」や「分類」を定義する層。
*   **【概念】タクソノミー (Taxonomy):** 概念のツリー状の階層分類。（例：「温度センサー」は「センサー」の一種）
*   **【概念】オントロジー (Ontology):** 階層分類に加え、「どの概念が、どの概念と、どう繋がるか」という関係性や制約の厳密なルール。（例：「機器」は「センサー」を[持つ]）
*   **【モデル】トリプル (Triple):** 情報を「主語 - 述語 - 目的語」の3要素で表現する基本形式。
*   **【モデル】プロパティグラフ (Property Graph):** ノードやエッジ自体にキー・バリュー型の属性（プロパティ）を格納できるモデル。現在の実務で主流。
*   **【実装規格】RDF / OWL:** オントロジーやトリプルをコンピュータが読み込めるように記述するW3Cの標準規格。

### Layer 2: データ・インスタンス層（知識の実体と保存）
Layer 1の設計図に従って、現実世界の具体的なデータを流し込み、保存する層。
*   **【概念】ナレッジグラフ (Knowledge Graph):** 実データの繋がり。「プレス機1号」→(持つ)→「温度センサーA」といった具体的な情報の集合体。
*   **【概念】エンティティ / ノード / エッジ:** グラフを構成する要素。「エンティティ(実体)」は「ノード(点)」として表現され、関係性は「エッジ(線)」で結ばれる。
*   **【実装製品】グラフデータベース:** ネットワーク構造をそのまま保存・高速探索できる専用DB。
    *   **代表製品:** Neo4j, Amazon Neptune, GraphDB

### Layer 3: セマンティック・クエリ層（意味の解釈とアクセス）
複雑なデータ構造を隠蔽し、人間やAIが「意味のある問い」を投げかけて情報を引き出す層。
*   **【概念】セマンティックレイヤー (Semantic Layer):** 「過熱エラーの原因機器は？」といったビジネスの問いを、裏側のDBへの探索処理に翻訳する仲介役。
*   **【概念】マルチホップ推論 (Multi-hop Reasoning):** グラフのリンクを複数回辿ることで、直接は繋がっていない情報を導き出す推論プロセス。
*   **【実装言語】クエリ言語:** グラフデータを検索・操作する言語。
    *   **Cypher:** プロパティグラフ（Neo4j等）で使われる直感的な言語。事実上の業界標準。
    *   **SPARQL:** RDF形式（セマンティックWeb）で使われるW3C標準言語。

### Layer 4: アプリケーション・活用層（AI連携）
引き出した知識を使って価値を生み出す層。現在最も注目されているのがLLMとの連携です。
*   **【概念】ナレッジ抽出 (Knowledge Extraction):** LLM等を用いて、テキスト（マニュアル等）からエンティティと関係性を自動抽出し、グラフを構築する処理。
*   **【実装アーキテクチャ】GraphRAG:** ナレッジグラフを検索基盤としてLLMに繋ぐ手法。

## 2. なぜ今ナレッジグラフなのか？（Vector RAG vs GraphRAG）

生成AI（LLM）の「ハルシネーション（嘘）」を防ぐ外部記憶として、従来のベクトル検索（通常のRAG）の弱点をGraphRAGが補完します。

| 比較項目 | Vector RAG（通常のRAG） | GraphRAG（ナレッジグラフ活用） |
| :--- | :--- | :--- |
| **検索の仕組み** | 文章の意味的類似度（ベクトル空間上の距離）で検索 | 定義されたエンティティの「関係性の線（エッジ）」を辿って検索 |
| **得意な問い** | 「XXの仕様について書かれたドキュメントを教えて」 | 「システム全体の構成を教えて」「AとBはどういう関係？」 |
| **弱点** | 情報が複数ドキュメントに分散している構造的な問いに弱い | グラフの事前の設計（オントロジー）とデータ構築に手間がかかる |

## 3. 実装例：Pythonによる構築とセマンティック検索

製造業の異常検知をテーマに、NetworkXライブラリを用いて「概念（Layer 1）」から「探索（Layer 3）」までを一貫して実装するコード例です。

```python
import networkx as nx

# ==========================================
# Layer 2: データ・インスタンス層 (Knowledge Graph)
# ==========================================
G = nx.DiGraph()

# 【Layer 1: オントロジー（ルール）の意識】
# 機器(Machine)はセンサー(Sensor)を持ち(HAS_SENSOR)、センサーは事象(Event)を検知する(DETECTS)

# ノード（エンティティ）の追加。type属性でタクソノミー（分類）を表現。
G.add_node("Press_Machine_01", type="Machine", location="Line_A")
G.add_node("Temp_Sensor_A", type="Sensor", measure="Temperature")
G.add_node("Vibration_Sensor_B", type="Sensor", measure="Vibration")
G.add_node("Error_Overheat_001", type="Event", severity="High")

# エッジ（関係性）の追加。relation属性でオントロジー上のつながりを表現。
G.add_edge("Press_Machine_01", "Temp_Sensor_A", relation="HAS_SENSOR")
G.add_edge("Press_Machine_01", "Vibration_Sensor_B", relation="HAS_SENSOR")
G.add_edge("Temp_Sensor_A", "Error_Overheat_001", relation="DETECTS")


# ==========================================
# Layer 3: セマンティック・クエリ層 (Semantic Layer)
# ==========================================
# ビジネスの問い：「特定のエラーが発生したとき、影響を受ける機器はどれか？」
# この複雑なグラフ探索（マルチホップ推論）を関数として隠蔽する。

def find_affected_machine(graph, event_name):
    # ホップ1: エラーイベントに向かっているエッジ（原因となったセンサー）を探す
    sensors = [src for src, dst, data in graph.in_edges(event_name, data=True) 
               if data.get("relation") == "DETECTS"]
    
    affected_machines = []
    for sensor in sensors:
        # ホップ2: そのセンサーに向かっているエッジ（センサーを所有する機器）を探す
        machines = [src for src, dst, data in graph.in_edges(sensor, data=True) 
                    if data.get("relation") == "HAS_SENSOR"]
        affected_machines.extend(machines)
        
    return affected_machines

# ==========================================
# Layer 4: アプリケーション層への応用イメージ
# ==========================================
# AIエージェントは、裏側の複雑なグラフ構造（CypherやNetworkXの仕様）を知らなくても、
# セマンティック層（find_affected_machine関数）をToolとして実行するだけで正解を得られる。

target_event = "Error_Overheat_001"
result = find_affected_machine(G, target_event)

print(f"対象イベント: {target_event}")
print(f"影響を受ける機器: {result[0]}") 
# 出力結果: 影響を受ける機器: Press_Machine_01

```


4. 直感的なアナロジー（家づくりでの例え）

| レイヤー | 用語 | 家づくりに例えると | プログラム・システムでの役割 |
| :--- | :--- | :--- | :--- |
| **Layer 1** | **タクソノミー** | 「建材」のカタログ分類（木材、ガラス...） | データの「種類（type）」の定義 |
| **Layer 1** | **オントロジー** | 家の「設計図」（窓は壁につく、ドアは玄関に） | 「どのtypeとtypeが繋がるか」のルール |
| **Layer 2** | **ナレッジグラフ** | 実際に建った「家そのもの」（Aさん宅の東側の窓） | 実データが入ったネットワーク基盤 |
| **Layer 3** | **セマンティック層** | 家の「API窓口」（照明スイッチ・音声コマンド受付口） | 人間/AIの"意図・問い"をDB操作に変換する**翻訳者・仲介役**（例：`find_affected_machine()` 関数） |
| **Layer 4** | **アプリケーション** | 「住人・AIロボット（音声アシスタント含む）」 | API窓口（Layer 3）を呼び出して実際に価値を生み出す**利用者・消費者** |
