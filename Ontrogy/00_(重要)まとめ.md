## 1. 全体像：セマンティック（意味論）という大きな傘

### 核心的な整理

「**セマンティック（Semantics = 意味論）**」と「**オントロジー（Ontology）**」は並列関係ではなく、**包含・階層の関係**にある。

```text
┌─────────────────────────────────────────────────────┐
│            セマンティック（Semantics）                  │
│     データに「意味」や「文脈」を持たせる思想・技術全体     │
│                                                     │
│  ┌──────────────────────────────────────────────┐    │
│  │ 具体的な手段（緩い → 厳密）                     │    │
│  │                                              │    │
│  │  ① グロッサリー / データカタログ（人間向け）     │    │
│  │  ② シソーラス（同義語・類義語の体系化）         │    │
│  │  ③ タクソノミー（階層分類）                    │    │
│  │  ④ オントロジー（論理・推論可能な最高峰モデル）  │    │
│  └──────────────────────────────────────────────┘    │
│                                                     │
│  ┌──────────────────────────────────────────────┐    │
│  │ 実装・運用の仕組み                              │    │
│  │                                              │    │
│  │  ● セマンティックレイヤー（BI/AI向け翻訳層）    │    │
│  │  ● ナレッジグラフ（オントロジーの具現化基盤）    │    │
│  │  ● データカタログ（メタデータ管理ツール）        │    │
│  └──────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────┘
```

> **ポイント**: セマンティックは「データに意味を持たせるぞ！」という技術トレンドや思想全体の名前。オントロジーはその中で最も厳密に体系化された手段。カラムの命名規約からOWLによる推論まで、すべて「セマンティック」の傘の下にある。

## 2. 知識表現のグラデーション（4段階モデル）

データに意味を持たせるアプローチは、「緩い（人間向け）」から「厳密（コンピュータ向け）」まで段階的に進化する。工場のセンサーデータを例に整理する。

### 一覧表

| レベル | 名称 | 内容 | センサーデータの例 | コンピュータの理解度 |
| :---: | :--- | :--- | :--- | :---: |
| **①** | **グロッサリー**（Glossary / 用語集） | 用語の定義や説明を自然言語で記述 | 「`temperature1` は機器Aの外側に取り付けた温度センサーの値です」 | ❌ テキストとしてのみ認識 |
| **②** | **シソーラス**（Thesaurus / 類語辞書） | 同義語・類義語・関連語の対応関係を定義 | 「温度」≒「気温」≒「Temperature」/ 「異常」→ 上位語:「イベント」 | △ 表記揺れの吸収が可能 |
| **③** | **タクソノミー**（Taxonomy / 分類体系） | 概念を親子関係（Is-A）で階層的に分類 | `計測器 > センサー > 温度センサー > 熱電対` | ○ 系統的な分類を理解 |
| **④** | **オントロジー**（Ontology / 知識体系） | 多角的な関係性 + 論理ルール + 推論規則 | 「温度センサーは機器Aに[設置されている]」「温度がX度以上なら[異常状態]」 | ◎ 自動推論が可能 |

### 階段図

```text
 [厳 密]  ▲  ④ オントロジー (Ontology)
          │      └ コンピュータが「機器Aの故障リスク」を推論できる論理的な知識ネットワーク
          │  ③ タクソノミー (Taxonomy)
          │      └ 「温度センサー」は「計測器」の一種である、という親子・階層関係
          │  ② シソーラス (Thesaurus)
          │      └ 「温度」「Temperature」「気温」は同じ概念を指す、という同義・関連語の体系
 [緩 い]  │  ① グロッサリー (Glossary)
          ▼      └ 「temperature1は機器Aの外側の温度」という、人間が読むための辞書・説明文
```

### 各段階の詳細

#### ① グロッサリー（Glossary / 用語集）

- **レベル**: 緩い（人間向け）
- **内容**: 用語の定義や説明文を自然言語で記述
- **実務でのツール**: データカタログ（DataHub, Atlan, OpenMetadata 等）、Confluence、Notion
- **限界**: コンピュータにとってはただの「テキスト（文字列）」。機械的な処理には使えない

#### ② シソーラス（Thesaurus / 類語辞書）

- **レベル**: 緩い〜中間（表記揺れの吸収）
- **内容**: 同義語（synonym）、上位語（broader）、下位語（narrower）、関連語（related）の対応関係を定義
- **実務での活用**:
  - 検索システムで「温度」と入力したら「Temperature」「気温」のデータも検索結果に含める
  - データ統合時の名寄せ（Entity Resolution）の基盤として機能
- **代表例**: MeSH（医学用語シソーラス）、SKOS（Simple Knowledge Organization System：W3C標準）
- **タクソノミーとの違い**: タクソノミーは「Is-A（〜は〜の一種）」の階層関係のみ。シソーラスは「同義」「関連」といった多様な意味関係を扱う

#### ③ タクソノミー（Taxonomy / 分類体系）

- **レベル**: 中間（階層化）
- **内容**: 概念を「親子関係（Is-A関係）」で整理した分類ツリー
- **実務での活用**:
  - マスタデータの階層管理（商品カテゴリ、組織構造、設備分類）
  - BI ツールのドリルダウン軸
- **例**: `機器A > コンポーネント > センサー > 温度センサー > 熱電対`
- **限界**: 階層（Is-A）関係しか表現できない。「AはBに設置されている」のような横断的な関係は表現不可

#### ④ オントロジー（Ontology / 知識体系）

- **レベル**: 最も厳密（コンピュータが推論可能）
- **内容**: 以下の3要素をセットで保持
  1. **概念（クラス）の定義**: 「温度センサー」「機器」「異常イベント」
  2. **関係性（プロパティ）の定義**: 「〜に設置されている」「〜を計測する」
  3. **論理的なルール（推論規則）**: 「温度がX度以上 → 異常状態」「is_part_of は推移的」
- **実装技術**: OWL（Web Ontology Language）、RDF/RDFS
- **オントロジーの実体化（実装）**: ナレッジグラフ

## 3. オントロジーとナレッジグラフの関係

### 核心：「設計図」と「実体」の関係

オントロジーとナレッジグラフは、**TBox（Terminological Box）**と**ABox（Assertion Box）**の関係にある。

| 概念 | 役割 | データベースでの例え | 記述する内容 |
| :--- | :--- | :--- | :--- |
| **オントロジー（TBox）** | 知識の枠組み・設計図 | テーブル定義（スキーマ / DDL） | 「人間」「会社」というクラスの定義や、「〜に所属する」という関係性のルール |
| **ナレッジグラフ（ABox）** | 知識の実体・具現化 | レコード（データそのもの） | 「田中さん（人間）は、A社（会社）に所属する」という具体的な事実（トリプル）の集合 |

> **結論**: 「ナレッジグラフは、オントロジーを実現（実装）する手段」という理解は100%正しい。オントロジーが定義した知識の構造を、アプリケーションや検索で使えるように具現化したデータ基盤がナレッジグラフである。

### データモデルの種類

ナレッジグラフの内部データモデルには、大きく2つの方式がある。

| データモデル | 特徴 | 主なクエリ言語 | 主な製品 | 適した用途 |
| :--- | :--- | :--- | :--- | :--- |
| **RDF（トリプル）** | W3C標準。「主語-述語-目的語」の3要素で表現。Web規模のデータ連携に強い | SPARQL | GraphDB, Stardog, Apache Jena | セマンティックWeb、Linked Data、学術データ |
| **プロパティグラフ（LPG）** | ノード・エッジ自体に属性（キー・バリュー）を持てる。直感的で実務向き | Cypher, Gremlin | Neo4j, Amazon Neptune, TigerGraph | アプリケーション内のグラフ分析、GraphRAG |

### オントロジーの3構成要素とOWLの位置づけ

```text
+------------------------------------------+
|              Logic / Rules               |
+------------------------------------------+
                     |
+------------------------------------------+
|                   OWL                    | ← 推論・制約を定義
|            (Ontology Layer)              |
+------------------------------------------+
                     |
+------------------------------------------+
|                  RDFS                    | ← 基本的な階層構造を定義
|           (Vocabulary Layer)             |
+------------------------------------------+
                     |
+------------------------------------------+
|                   RDF                    | ← 事実（トリプル）を記述
|               (Data Layer)               |
+------------------------------------------+
```

| 層 | 役割 | できること |
| :--- | :--- | :--- |
| **RDF** | 事実の記述 | 「センサーAは温度センサーである」「センサーAは工場Xに設置されている」 |
| **RDFS** | 基本構造の定義 | 「温度センサー」は「計測機器」のサブクラス（タクソノミー相当） |
| **OWL** | 論理・ルールの定義 | 「排他性」「転移性」「逆関係」「等価クラス」など高度な推論ルール |

## 4. セマンティックレイヤー

### 位置づけ：概念の世界と物理データの仲介者

セマンティックレイヤーは、「概念の世界（セマンティック/オントロジー）」と「物理的な世界（SQL のテーブルやカラム）」をつなぐ **「実務的な翻訳ミドルウェア」** である。

```text
 [利用層]   BIツール（Looker/Tableau） や AIエージェント（Text-to-SQL）
              ▲
              │（ビジネス用語で安全にクエリを投げる）
 ┌────────────┼────────────────────────────────────────┐
 │ 意味の世界 │                                        │
 │            ▼                                        │
 │  ● オントロジー / ナレッジグラフ（論理・推論の頂点）     │
 │                                                     │
 │  ● セマンティックレイヤー（実務的な翻訳・集計ルール）  │
 │      └ メトリクス（計算式）、ディメンション、結合の定義   │
 │                                                     │
 │  ● グロッサリー / データカタログ（人間向けの説明）       │
 └────────────┬────────────────────────────────────────┘
              │（裏側で複雑なSQLに自動変換）
              ▼
 [物理層]   データベース（Snowflake / BigQuery / 各種ファイル）
            └ sensor_data1, tbl_m_equip_location などの生テーブル
```

### オントロジーとの違い

| 切り口 | セマンティックレイヤー | オントロジー / ナレッジグラフ |
| :--- | :--- | :--- |
| **主な目的** | 誰が（あるいはAIが）集計しても「指標の計算結果や結合ルール（SQL）」がブレないようにする | 複雑な現実世界の「概念の関係性」を整理し、コンピュータに「論理的な推論」をさせる |
| **定義するもの** | メトリクス、ディメンション、結合（Join）ルール | クラス（概念）、関係性（プロパティ）、推論規則 |
| **実務での例え** | データアクセス用の、意味付けされたビュー（API） | データ同士がどうつながっているかの、脳内マップ |

### センサーデータの例で見る違い

**セマンティックレイヤーでの定義**:
> 「`sensor_data1` のカラム名を `equipment_temperature` として公開します。これは、過去5分間の移動平均（`AVG() OVER...`）として計算するメトリクスです。`equipment_master` テーブルとは `equip_id` で自動結合します」
>
> → 結果：ユーザーやAIが「設備温度の平均を教えて」と頼むだけで、正しいSQLが自動生成される

**オントロジーでの定義**:
> 「設備温度 は 物理量 であり、温度センサー によって 計測 される。温度センサー が 故障状態 にあるとき、そこから得られる 設備温度 の信頼度は 低 になる」
>
> → 結果：コンピュータが「センサーが故障しているから、この温度データは異常値ではなく無視すべきだ」と裏で判断（推論）できる

### なぜ今セマンティックレイヤーが必要なのか

LLM（生成AI）やAIエージェントの台頭が、セマンティックレイヤーの価値を爆発させている。

- AIに生のデータベース（`sensor_data1` のようなカオスなテーブル群）をそのまま見せると、**SQLの結合を間違えたり、計算ロジックを捏造（ハルシネーション）**したりする
- セマンティックレイヤーを挟むことで、AIは複雑なSQLを書く必要がなくなり、ビジネス言語のままで正確なデータを安全に引き出せる

### 主要なツール / 規格

| カテゴリ | 名称 | 特徴 |
| :--- | :--- | :--- |
| **ツール** | dbt Semantic Layer (MetricFlow) | Metrics-as-Code。YAML で定義し、Git管理 |
| **ツール** | Cube | ユニバーサルセマンティックレイヤー。REST/GraphQL API を提供 |
| **ツール** | LookML (Looker) | Looker 独自のモデリング言語 |
| **規格** | Open Semantic Interchange (OSI) | ツール間でセマンティック定義を持ち運ぶための共通規格（YAML形式）。"Write Once, Query Anywhere" を実現 |

## 5. データマネジメントの周辺概念

セマンティックやオントロジーだけでは不十分であり、データの「信頼性」を担保するには以下の周辺概念も不可欠である。

### 5.1 メタデータ管理（Metadata Management）

データの「データ」を体系的に管理する取り組み。メタデータには以下の種類がある。

| 種類 | 内容 | 例 |
| :--- | :--- | :--- |
| **テクニカルメタデータ** | スキーマ定義、データ型、制約 | `temperature1 FLOAT NOT NULL` |
| **ビジネスメタデータ** | ビジネス上の意味、オーナー、利用目的 | 「機器Aの外側温度。品質管理部が使用」 |
| **オペレーショナルメタデータ** | 更新日時、データ件数、ジョブ実行状況 | 「最終更新: 2026-06-14 08:00 / 10万件」 |

### 5.2 データガバナンス（Data Governance）

データの品質、セキュリティ、プライバシー、コンプライアンスを組織的に管理するための**ポリシー・プロセス・体制**。

- **データスチュワード**: データの品質と定義の正確性を維持する責任者
- **データリネージ（Data Lineage）**: データがどこから来て、どう変換されて、どこで使われているかの追跡
- **データ品質（Data Quality）**: 正確性、完全性、一貫性、適時性の担保
- **アクセス制御**: 誰がどのデータにアクセスできるかのポリシー管理

### 5.3 マスターデータ管理（MDM: Master Data Management）

組織全体で共有される基幹データ（顧客、商品、設備、従業員など）の「唯一の正しい情報源（Single Source of Truth）」を確立・維持する取り組み。

- オントロジーやタクソノミーで定義した概念の「実体（マスターレコード）」を管理する役割
- 名寄せ（Entity Resolution）や表記揺れの統合が主要なタスク

### 5.4 データ契約（Data Contract）

データの提供者（プロデューサー）と利用者（コンシューマー）の間で交わす、データの品質・スキーマ・SLAに関する合意。データメッシュなどの分散型アーキテクチャで重要性が増している。

### 5.5 Linked Data（リンクトデータ）

Web上でデータを公開・相互リンクするための4原則（Tim Berners-Lee提唱）：

1. URI を使って物事を識別する
2. HTTP URI を使い、参照可能にする
3. URI が参照されたら、RDF/SPARQL等の標準を使って有用な情報を返す
4. 他のURIへのリンクを含め、他のデータを発見できるようにする

> **セマンティックWebとの関係**: Linked Data はセマンティックWebのビジョンを実現するための具体的な実践方法。オントロジー（OWL）とナレッジグラフ（RDF）はその技術基盤となる。

## 6. テクノロジースタック（4層レイヤーモデル）

データを「意味を持ったネットワーク」として扱うための技術体系を4層で整理する。

### Layer 1: スキーマ・モデリング層（設計図とルールの定義）

世界をどのようにデータ化するか、その「型」や「分類」を定義する層。

| 区分 | 名称 | 説明 |
| :--- | :--- | :--- |
| 概念 | タクソノミー | 概念のツリー状の階層分類 |
| 概念 | オントロジー | 階層分類 + 関係性 + 制約の厳密なルール |
| モデル | トリプル | 「主語-述語-目的語」の3要素で情報を表現する基本形式 |
| モデル | プロパティグラフ | ノード・エッジ自体に属性を格納できるモデル（実務の主流） |
| 実装規格 | RDF / OWL | オントロジーやトリプルを記述するW3C標準規格 |

### Layer 2: データ・インスタンス層（知識の実体と保存）

Layer 1 の設計図に従って、現実世界のデータを流し込み、保存する層。

| 区分 | 名称 | 説明 |
| :--- | :--- | :--- |
| 概念 | ナレッジグラフ | 実データのネットワーク構造 |
| 概念 | エンティティ / ノード / エッジ | グラフの構成要素 |
| 実装製品 | グラフデータベース | Neo4j, Amazon Neptune, GraphDB 等 |

### Layer 3: セマンティック・クエリ層（意味の解釈とアクセス）

複雑なデータ構造を隠蔽し、人間やAIが「意味のある問い」を投げかけて情報を引き出す層。

| 区分 | 名称 | 説明 |
| :--- | :--- | :--- |
| 概念 | セマンティックレイヤー | ビジネスの問いを裏側のDB探索に翻訳する仲介役 |
| 概念 | マルチホップ推論 | グラフのリンクを複数回辿って間接的な情報を導出 |
| 実装言語 | Cypher | プロパティグラフ向け（Neo4j等）。事実上の業界標準 |
| 実装言語 | SPARQL | RDF向け。W3C標準 |
| 実装言語 | Gremlin | グラフ巡回型のプログラマティックな言語 |

### Layer 4: アプリケーション・活用層（AI連携と価値創出）

引き出した知識を使って価値を生み出す層。

| 区分 | 名称 | 説明 |
| :--- | :--- | :--- |
| 概念 | ナレッジ抽出 | LLM等でテキストからエンティティ・関係性を自動抽出 |
| アーキテクチャ | GraphRAG | ナレッジグラフを検索基盤としてLLMに接続する手法 |
| アーキテクチャ | Vector RAG | ベクトル空間上の類似度で検索する手法（通常のRAG） |

### Layer 3 と Layer 4 の違い

| | Layer 3：セマンティック層 | Layer 4：アプリケーション層 |
| :--- | :--- | :--- |
| **役割** | **翻訳者・仲介役** | **利用者・消費者** |
| **何をするか** | 人間/AIの意図をDB操作に変換 | セマンティック層を呼び出して価値を生む |
| **具体例** | `find_affected_machine()` 関数、CypherクエリのAPI | AIエージェント、BIダッシュボード |
| **家のアナロジー** | 照明スイッチ、音声コマンド受付口 | 住人・AIロボット |

## 7. 実装技術の詳細

### 7.1 OWL（Web Ontology Language）の真骨頂

OWLがただのスキーマと決定的に違うのは、**リーゾナー（Reasoner：推論エンジン）** を通して、明示的に書かれていない新しい事実を自動的に導き出せる点。

#### プロパティの特性

| 特性 | 説明 | 例 |
| :--- | :--- | :--- |
| **転移性** (Transitive) | A→B、B→C なら A→C | 「部品Aは装置Bの一部」+「装置BはラインCの一部」→「部品AはラインCの一部」 |
| **対称性** (Symmetric) | A→B なら B→A | 「部屋Aは部屋Bに隣接」→「部屋Bは部屋Aに隣接」 |
| **逆関係** (Inverse Of) | `hasPart` の逆は `isPartOf` | 片方を書くだけで双方向リンクが完成 |

#### クラスの論理演算

| 演算 | 説明 | 例 |
| :--- | :--- | :--- |
| **排他性** (Disjoint) | 2つのクラスは重複不可 | `NormalStatus` と `ErrorStatus` に同時所属 → 矛盾エラー |
| **等価性** (Equivalent) | 条件を満たすものを自動分類 | 「温度 ≥ 100℃ かつ 圧力が異常」→ `DangerState` に自動分類 |

#### RDFS との比較

| やりたいこと | RDFS | OWL |
| :--- | :---: | :---: |
| サブクラスの定義 | ✓ | ✓ |
| プロパティの適用範囲の指定 | ✓ | ✓ |
| クラスの排他性 | ✗ | ✓ (`owl:disjointWith`) |
| 逆関係の定義 | ✗ | ✓ (`owl:inverseOf`) |
| 集合演算（交差・和集合） | ✗ | ✓ (`owl:intersectionOf`) |

### 7.2 Open Semantic Interchange (OSI)

セマンティックレイヤーのベンダーロックインを解消する共通規格。

```text
【 物理レイヤー 】 Snowflake / Databricks / BigQuery 等
       ↓
【 定義・変換レイヤー 】 dbt / Cube / Looker / Salesforce（各製品の内部定義）
       ↓ 
★【 共通相互運用レイヤー：OSI (Open Semantic Interchange) 】★
       ↓ （共通のYAML形式でどこへでも持ち運べる）
【 消費レイヤー 】 各種BI、ThoughtSpot、AIエージェント（Text-to-SQL等）
```

- **目的**: "Write Once, Query Anywhere"（1つの定義をどこでも使える）
- **形式**: YAML（JSONも並行サポート）。人間にとっての可読性、GitOps/Diff との親和性を重視
- **参加企業**: Snowflake, Salesforce, dbt Labs, Cube 等
- **JSON-LDとの違い**: JSON-LD は Web 上のエンティティをグラフ（RDF）で繋ぐ規格。OSI は BI/AI 向けの SQL ロジック・メトリクス定義の共通化が目的

### 7.3 Vector RAG vs GraphRAG

| 比較項目 | Vector RAG（通常のRAG） | GraphRAG（ナレッジグラフ活用） |
| :--- | :--- | :--- |
| **検索の仕組み** | 文章の意味的類似度（ベクトル空間上の距離）で検索 | エンティティの関係性の線（エッジ）を辿って検索 |
| **得意な問い** | 「XXの仕様書はどれ？」 | 「システム全体の構成は？」「AとBの関係は？」 |
| **弱点** | 複数ドキュメントにまたがる構造的な問いに弱い | グラフの設計（オントロジー）とデータ構築に手間がかかる |

## 8. 現代の AI・LLM 文脈における変化

### トップダウン → ボトムアップへの変化

| 時代 | アプローチ | 特徴 |
| :--- | :--- | :--- |
| **伝統的** セマンティックWeb | **トップダウン** | まず厳密なオントロジー（OWL/RDF）を設計 → データを流し込む |
| **現代** LLM/GraphRAG | **ボトムアップ** | LLMで非構造化データからエンティティ・関係性を自動抽出 → ナレッジグラフを構築 |

### ボトムアップでもオントロジーは必要

ボトムアップなアプローチでも、以下の問題を防ぐために「緩やかなスキーマ」としてオントロジー的ガイドラインが必要：

- **表記揺れ**: 同じエンティティが異なる名前でノード化される
- **関係性の不統一**: 「所属する」「勤める」「働く」が別々の関係として定義される
- **過度な一般化・詳細化**: 粒度がバラバラなグラフになり、検索精度が低下する

### AIエージェント時代の鍵

1. **セマンティックレイヤー**: AIが正確なSQLを生成するための「信頼できる辞書」
2. **ナレッジグラフ + GraphRAG**: AIの外部記憶装置。ハルシネーション抑制と構造的推論の基盤
3. **オントロジー**: AIが「データの意味」を正しく理解するための論理的フレームワーク
